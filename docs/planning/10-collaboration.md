# 10. 협업 규칙

## 브랜치
- `main` — 배포 브랜치. develop에서 릴리스 PR로만 들어간다
- `develop` — 기본 브랜치
- `feature/{이니셜}/{작업}` → develop PR, 머지 후 브랜치 자동 삭제

## 커밋
`type: 한국어 요약` — feat · fix · refactor · test · docs · chore
본문에 "왜" 바꿨는지를 적는다.

## 코드 리뷰
- PR은 400줄 이하로 나눈다. 템플릿: 변경 사항 · 확인 방법 · 스크린샷(화면)
- 승인 1명 이상 + CI 통과 후 머지. 점검 엔진 · 보안 관련 변경은 QA/SEC 승인 필수
- 리뷰는 24시간 안에. 제안은 `[필수]` / `[제안]` / `[질문]` 머리말로 구분

## 회의
| 회의 | 주기 | 내용 |
|---|---|---|
| 데일리 스크럼 | 평일 10분 (비동기 슬랙 가능) | 어제 · 오늘 · 막힌 것 |
| 스프린트 계획 | 2주마다 | 백로그 우선순위, 담당 배정 |
| 스프린트 리뷰 · 회고 | 2주마다 | 데모, KPT 회고 |
| 주간 설계 회의 | 주 1회 | ADR 결정 |

## 완료 기준 (Definition of Done)
- 인수 조건 충족, 단위 · 통합 테스트 추가, CI 통과
- API 변경은 07. API 명세 갱신, 스키마 변경은 Flyway 마이그레이션
- 화면은 모바일 폭 · 키보드 조작 확인
- 점검 항목 추가는 오탐 테스트(정상 사이트 · SPA 200 응답) 포함
