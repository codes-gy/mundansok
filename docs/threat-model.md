# 위협 모델

문단속은 **남의 서버에 요청을 대신 보내 주는** 서비스다. 그래서 (1) 우리 서버가 내부망을 찌르는 발판(SSRF)이 되거나,
(2) 남의 도메인을 대신 점검해 주는 정찰 도구가 되거나, (3) 남의 점검 결과(=약점 목록)가 새어 나가는 것을 가장 경계한다.

## 지키는 것
| 자산 | 왜 중요한가 |
|---|---|
| 서버가 닿는 내부망 · 클라우드 메타데이터(169.254.169.254 등) | 점검 요청이 내부로 향하면 SSRF |
| 점검 결과 | 노출 파일 · 약한 설정 목록이라 공격자에게는 정찰 결과 |
| "이 도메인의 주인" 이라는 상태 | 주인만 점검을 시킬 수 있어야 남의 도메인을 대신 두드리지 않는다 |
| 점검 대상 서버 | 점검 요청이 과하면 그 자체로 부하 · 스캔으로 보인다 |

## 공격자와 방어

### 1. SSRF — 내부 주소로 요청을 보내게 만들기
- **내부 대역 차단** (`net/AddressGuard`): 호스트가 풀리는 IP 중 하나라도 공인 주소가 아니면 요청하지 않는다.
  - IPv4: 0/8 · 10/8 · 100.64/10(CGNAT) · 127/8 · 169.254/16 · 172.16/12 · 192.0.0/24 · 192.88.99/24 · 192.168/16 · 198.18/15 · 224/4 이상
  - IPv6: `::`, `::1`, fe80::/10, fec0::/10, fc00::/7, 멀티캐스트, 2001:db8::/32, 100::/64
  - **IPv4를 품은 IPv6**: IPv4-mapped(`::ffff:a.b.c.d`) · IPv4-compatible(`::a.b.c.d`)는 안의 IPv4로 판단하고,
    NAT64(`64:ff9b::/96`, `64:ff9b:1::/48`) · 6to4(`2002::/16`) · Teredo(`2001::/32`)는 안의 주소와 관계없이 막는다.
- **DNS 리바인딩(TOCTOU) 차단**: 검사할 때와 연결할 때 이름을 각각 풀면, TTL 0 DNS가 처음엔 공인 IP · 다음엔 내부 IP를 줘서 검사를 통과할 수 있다.
  - HTTP(`net/JdkHttpProbe`): `java.net.http.HttpClient`는 send 할 때 이름을 다시 풀기 때문에 쓰지 않는다.
    이름을 **한 번만** 풀어 검사한 뒤, 소켓을 **그 IP로 직접** 연결하고 도메인 이름은 `Host` 헤더 · TLS SNI · 인증서 호스트 이름 검증에만 쓴다.
  - TLS(`net/JdkTlsInspector`): 같은 방식으로 검사한 IP에 연결하고 SNI · 엔드포인트 확인(`HTTPS`)은 도메인 이름으로 한다.
  - 테스트: 첫 조회는 공인 IP, 두 번째는 내부 IP를 주는 가짜 리졸버로 "검사한 IP로만 연결하고 이름을 다시 풀지 않는다"를 확인한다
    (`JdkHttpProbeTest`, `JdkTlsInspectorTest`).
- **리다이렉트는 따라가지 않는다**. `Location`은 값만 읽는다.
- **입력 제한** (`domain/DomainNames`): IP 리터럴 · `localhost` · `.local` · `.internal` 은 등록부터 거절한다.
- 요청 하나에 전체 시간 제한(기본 5초)을 걸고, 응답은 헤더 64KB · 본문 앞 2KB만 읽는다.

### 2. 남의 도메인을 점검하게 만들기 · 소유권 가로채기
- **등록마다 소유자 토큰**: `POST /api/domains`는 등록할 때마다 새 등록(`domain_claim`)과 256비트 소유자 토큰을 만든다.
  토큰 평문은 그 응답에서 한 번만 주고, DB에는 SHA-256만 남긴다. 인증 · 점검 · 결과 조회는 `Authorization: Bearer <토큰>`이 있어야 한다.
- **기존 토큰을 흘리지 않는다**: 같은 도메인을 다시 등록해도 기존 등록의 TXT 값 · 토큰 · 인증 상태를 돌려주지 않는다.
  각 등록은 자기 TXT 값으로 따로 인증해야 한다. (이전에는 같은 이름을 등록한 누구에게나 기존 토큰과 "인증됨" 상태가 넘어갔다.)
- **점검할 때마다 다시 확인**: 한 번 인증한 뒤에도 도메인이 팔리거나 레코드가 지워질 수 있으므로, 점검 요청마다 TXT 레코드를 다시 조회한다.
  없으면 `403 VERIFICATION_EXPIRED`.
- 토큰 비교는 상수 시간(`MessageDigest.isEqual`)으로 한다.

### 3. 남의 점검 결과 보기 (IDOR)
- API 식별자는 모두 **UUID**다(등록 id · 점검 id). 순번 id는 밖으로 내보내지 않는다.
- 결과(`GET /api/scans/{id}`)는 **그 점검을 요청한 등록의 소유자 토큰**으로만 볼 수 있다.
  없는 점검과 남의 점검은 구분하지 않고 `404`(존재 여부도 알려 주지 않는다). 토큰이 없으면 `401`.

### 4. 점검 남용 · 자원 고갈
- **도메인별 쿨다운**(기본 10분): 누가 요청했든 같은 도메인 이름 기준이다.
  확인과 기록을 `UPDATE domain SET last_scan_requested_at = :now WHERE id = :id AND (last_scan_requested_at IS NULL OR last_scan_requested_at <= :now - cooldown)`
  **한 문장**으로 해서, 동시에 요청이 몰려도 행 잠금 때문에 하나만 통과한다(이전에는 "최근 점검 조회 → 저장" 사이에 경쟁이 있었다).
  점검 풀이 가득 차 503으로 거절하면 받아 둔 쿨다운 자리를 되돌린다.
- **IP별 요청 제한** (`ratelimit/`): 등록 · 인증 · 점검 요청을 IP별 토큰 버킷으로 제한하고, 넘치면 `429 RATE_LIMITED` + `Retry-After`.
  기본값은 `application.yaml`의 `mundansok.rate-limit.limits`(등록 20 · 인증 30 · 점검 30 / 시간).
  - IP는 `request.getRemoteAddr()`다. `server.forward-headers-strategy=native`(Tomcat RemoteIpValve)는 사설 · 루프백 대역에서 온 요청의
    `X-Forwarded-For`만 믿으므로, 밖에서 직접 위조한 헤더로 제한을 피할 수 없다. 프록시가 사설망 밖이면 `server.tomcat.remoteip.internal-proxies`를 맞춘다.
  - **한계: 서버 한 대 기준**이다. 버킷은 메모리에 있어 여러 대로 띄우면 대수만큼 한도가 늘고, 재시작하면 초기화된다.
    여러 대로 운영할 때는 Redis 등 공유 저장소 기반(Bucket4j + Redis 등)이나 앞단 프록시 · WAF의 제한으로 바꿔야 한다.
- 점검 풀(스레드 4 · 대기열 100)이 차면 `503 SCAN_QUEUE_FULL`.

## 남은 위험 · 하지 않은 것
- **토큰 보관**: 웹 화면은 소유자 토큰을 브라우저 `localStorage`에 둔다. XSS가 생기면 토큰이 샐 수 있다. 토큰을 잃으면 다시 등록 · 인증해야 한다(재발급 없음).
- **결과 조회 횟수 제한 없음**: `GET` 요청은 IP 제한을 두지 않았다(UUID + 256비트 토큰이라 추측 공격은 현실적이지 않다고 봤다).
- **V2 이전 데이터**: 소유자 토큰이 없던 이전 등록 · 점검은 API로 접근할 수 없다(다시 등록 · 인증해야 한다).
- **도메인 이름 쪽 DNS(TXT · CAA) 조회**는 시스템 리졸버를 쓴다. 이 조회 결과로는 연결하지 않으므로 SSRF 경로는 아니다.
- **HTTP/2 · 프록시 미지원**: 점검 요청은 HTTP/1.1로만 보낸다. 서버가 아웃바운드 프록시를 거쳐야 하는 환경은 고려하지 않았다.
