# 문단속(Mundansok) 기획서

> 회사 도메인을 넣으면, 공격자가 밖에서 먼저 보게 될 약점을 찾아 쉬운 말로 알려 주는 외부 노출 점검 서비스

## 1. 왜 만드나

- AI 도구로 공격 준비가 쉬워지면서, 공격자는 사람이 손으로 하던 정찰(노출된 설정 파일, 만료된 인증서, 빠진 보안 헤더, 위조 가능한 메일 도메인 찾기)을 자동으로, 대량으로 돌린다.
- 반면 보안 담당자가 없는 작은 회사는 자기 서비스가 밖에서 어떻게 보이는지 확인할 방법이 마땅치 않다. 상용 점검 도구는 비싸고, 결과가 전문 용어로 가득하다.
- **목표**: 공격자가 먼저 찾기 전에, 회사가 같은 시선으로 자기 도메인을 점검하고 무엇부터 고칠지 알게 한다.

## 2. 누가 쓰나

- 보안 전담 인력이 없는 스타트업 · 중소기업의 개발자, 운영 담당자
- 외주로 만든 홈페이지 · 쇼핑몰을 운영하는 비개발 직군 (결과를 쉬운 말로 읽어야 함)

## 3. 원칙 — 공격 도구가 되지 않게

| 원칙 | 구현 |
|---|---|
| 내 도메인만 점검 | DNS TXT 레코드로 **도메인 소유를 인증한 뒤에만** 점검한다 |
| 공격하지 않고 확인만 | 공개된 주소에 일반 요청(GET)만 보낸다. 로그인 시도 · 대입 공격 · 포트 스캔 · 취약점 공격 코드 실행은 하지 않는다 |
| 내부망 차단 | 대상 호스트가 사설 · 루프백 · 링크 로컬 IP로 풀리면 요청하지 않는다(SSRF 방지) |
| 과한 요청 방지 | 도메인당 점검은 10분에 한 번, 요청마다 5초 타임아웃, 응답 본문은 앞 2KB만 읽는다 |
| 찾은 값은 최소한만 저장 | 노출된 파일 내용은 저장하지 않고 "노출됨"과 근거 요약만 남긴다 |

## 4. 점검 항목 (MVP)

| 점검 | 무엇을 보나 | 위험도 기준 |
|---|---|---|
| TLS 인증서 | 만료일, 호스트 이름 일치, 협상된 TLS 버전 | 만료 · 이름 불일치 · TLS 1.2 미만 = 높음, 14일 이내 만료 = 보통, 30일 이내 = 낮음 |
| HTTPS 전환 | `http://` 접속이 `https://`로 넘어가는지 | 안 넘어가면 보통 |
| 보안 헤더 | HSTS, CSP, X-Content-Type-Options, 클릭재킹 방지(X-Frame-Options · frame-ancestors), Referrer-Policy, Server 버전 노출 | 헤더별 보통 · 낮음 |
| 민감 파일 노출 | `/.git/HEAD`, `/.env`, `/actuator/env`, `/server-status`, `/phpinfo.php` | 소스 · 비밀 값 노출 = 높음, 서버 정보 노출 = 보통 |
| 메일 위조 방지 | SPF, DMARC 레코드와 정책 | 없음 = 보통, `+all` = 높음, DMARC `p=none` = 낮음 |

점수: 100점에서 높음 −20, 보통 −10, 낮음 −3 (최저 0).

## 5. 사용 흐름

```
도메인 등록 → TXT 레코드 안내(_mundansok-verify.<도메인> = mundansok-verify=<토큰>)
→ 소유 인증 → 점검 요청(비동기) → 결과: 점수 · 위험도별 항목 · 고치는 방법
```

## 6. 아키텍처

```
[Next.js 화면] ──REST──> [Spring Boot API]
                              ├─ DomainService  : 도메인 정규화 · 소유 인증(DNS TXT)
                              ├─ ScanService    : 점검 요청 · 10분 제한 · 비동기 실행
                              │    └─ Check × 5 : TLS · HTTPS 전환 · 보안 헤더 · 민감 파일 · 메일 위조 방지
                              │         └─ HttpProbe / TlsInspector / DnsResolver (외부 접근은 이 셋만, SSRF 가드 통과 후)
                              └─ PostgreSQL     : domain · scan · finding (Flyway)
```

- 점검 하나가 `Check` 인터페이스 하나 — 점검을 늘려도 다른 코드는 그대로다.
- 외부 접근(HTTP · TLS · DNS)은 인터페이스 뒤로 숨겨, 테스트는 가짜 구현으로 네트워크 없이 돈다.
- AI는 **판정에 쓰지 않는다.** 판정은 규칙으로 하고, AI는 결과를 "무엇이 위험하고 무엇부터 고칠지" 쉬운 말로 풀어 주는 데만 쓴다(2단계). 같은 입력이면 같은 판정이 나와야 하기 때문.

## 7. API (MVP)

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/domains` | 도메인 등록, 인증용 TXT 레코드 안내 |
| POST | `/api/domains/{id}/verify` | TXT 레코드 확인 후 소유 인증 |
| POST | `/api/domains/{id}/scans` | 점검 요청(인증된 도메인만, 10분에 한 번) — 202 |
| GET | `/api/scans/{id}` | 점검 상태 · 점수 · 결과 |

| 단계 | 내용 |
|---|---|
| 1단계 (지금) | 백엔드 MVP — 도메인 인증, 점검 5종, 비동기 실행, 점수, API, 테스트 |
| 2단계 | Next.js 화면 — 도메인 등록 · 인증 안내 · 결과 대시보드, 회원(팀) 단위 도메인 관리 |
| 3단계 | AI 설명 — 결과를 쉬운 말 요약 · 우선순위 · 고치는 방법(서버 종류별 설정 예시)으로 정리 |
| 4단계 | 정기 점검 · 알림 — 매주 자동 점검, 인증서 만료 · 새 노출 발견 시 메일 알림, 점수 추이 |

## 9. 알려진 한계 · 다음 고민

- DNS 리바인딩: 검사 시점과 요청 시점 사이에 IP가 바뀌는 경우 — 2단계에서 검증한 IP로 직접 연결하도록 바꾼다.
- 서브도메인 탐색(인증서 투명성 로그)은 범위가 커서 MVP에서 뺐다.
- TLS 1.0/1.1을 서버가 *지원하는지*는 JDK 클라이언트가 막아 확인할 수 없다 — 협상된 버전만 본다.
